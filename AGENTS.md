# Mini Godbolt Agent Operating Plan

This file defines how Codex and subagents should investigate, implement, audit, verify, and release this project.

## Current Project Snapshot

Mini Godbolt is a Windows-oriented single-exe C learning tool inspired by Compiler Explorer.

Repository layout:

- `cmd/mini-godbolt/main.go`: executable entrypoint.
- `internal/app`: Go backend, project persistence, compile/run, LSP bridge, source access, toolchain discovery, embedded stdlib headers, embedded static UI.
- `web`: Vite + TypeScript + Monaco frontend.
- `scripts/build.ps1`: production build script.
- `scripts/fetch-llvm.ps1`: downloads official LLVM, slims it, prepares sidecar and embedded toolchain zip.
- `docs/architecture.md`: runtime architecture notes.
- `README.md`: user/developer behavior summary.

Runtime model:

- The app starts a local HTTP server on `127.0.0.1`.
- Project files live in a project directory, defaulting to the desktop path in normal runtime.
- Third-party headers and source files are read from `include/` next to the exe.
- Built-in C17 declaration stubs are extracted into the cache and passed with `-isystem`.
- Toolchain discovery order is sidecar `toolchain/`, cached embedded zip extraction, embedded zip extraction, then `PATH`.
- The frontend is built into `internal/app/static`, then embedded by Go into `dist/mini-godbolt.exe`.

Important backend endpoints:

- `GET /api/status`
- `GET /api/project`
- `POST /api/project/sync`
- `POST /api/source/read`
- `POST /api/compile`
- `POST /api/run`
- `GET /api/lsp`

## Engineering Rules

- Do not revert user changes unless the user explicitly asks.
- Keep edits scoped to the requested behavior.
- Prefer existing local patterns over new abstractions.
- Prefer mature, maintained libraries for protocol parsing, network framing, archive handling, process isolation, language parsing, and other security-sensitive primitives. Do not hand-roll these when a practical library is available.
- Keep modules cohesive and reviewable. New frontend files should have one clear responsibility, imports before implementation, and no duplicate imports from the same module. Large files should be split before adding more behavior unless the split would create artificial coupling.
- Bias toward small, self-contained changes that improve code health. A change that affects build, release, runtime behavior, or user workflow must update tests and docs in the same commit.
- Treat raw `innerHTML`, custom parsers, archive extraction, path containment, process management, and network protocols as restricted APIs. Use maintained libraries or a documented wrapper with tests.
- Use `rg` for search.
- Use `apply_patch` for manual file edits.
- Avoid destructive filesystem operations. If cleanup is needed, identify exact targets first.
- Generated output, logs, temp folders, `dist/`, downloaded LLVM archives, and node modules should stay out of Git.
- Do not commit unless explicitly asked.

## Development Pipeline

1. Investigation
   - Read the relevant frontend and backend files before proposing or editing.
   - Identify the behavioral boundary: UI-only, backend-only, LSP, compiler/run, packaging, or cross-cutting.
   - Check existing tests and whether the change needs new coverage.

2. Plan
   - For small fixes, keep the plan brief.
   - For cross-cutting changes, list affected files, risks, and verification commands.
   - When subagents are requested, create bounded audit or implementation scopes with disjoint ownership.

3. Implementation
   - Frontend source edits go under `web/src`.
   - Backend source edits go under `internal/app` or `cmd`.
   - Static production UI is generated by `npm.cmd run build` from `web`.
   - The executable is generated by `scripts/build.ps1`.

4. Verification
   - Always run the narrowest meaningful check first.
   - Backend checks:
     - `go test ./...`
   - Frontend checks:
     - `npm.cmd run build` from `web`
   - Full production check:
     - `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\build.ps1`
   - Runtime status check:
     - Start `dist\mini-godbolt.exe -addr 127.0.0.1:57070 -no-browser`
     - Query `GET http://127.0.0.1:57070/api/status`
   - Browser/UI check:
     - Refresh `http://127.0.0.1:57070/`
     - Verify the exact workflow affected by the change.

5. Release Pipeline
   - Run `scripts/fetch-llvm.ps1` when preparing a release toolchain.
   - Confirm `internal/app/toolchains/llvm-windows-amd64.zip` exists before a true single-exe release build.
   - Run `scripts/build.ps1`.
   - Confirm `dist/mini-godbolt.exe` starts without requiring LLVM on `PATH`.
   - Confirm `dist/include` contains any intended third-party files copied from root `include/`.

6. Git Hygiene
   - Run `git status --short` before and after edits.
   - Stage only intended source, docs, scripts, and config files.
   - Keep `tmp-*`, logs, `dist/`, `downloads/`, `.gocache/`, and node modules ignored.

## Audit Plan

Run audits in parallel when requested. Each subagent must report findings first, ordered by severity, with file/function references and suggested verification. Subagents should not edit files unless explicitly assigned an implementation task.

### Audit A: Backend Compiler, Run, and Path Safety

Scope:

- `internal/app/compile.go`
- `internal/app/compiler_args.go`
- `internal/app/project.go`
- `internal/app/source.go`
- `internal/app/toolchain.go`
- backend tests under `internal/app/*_test.go`

Questions:

- Can user-controlled project paths escape the project root?
- Can `include/` or embedded toolchain extraction escape allowed roots?
- Are compiler arguments split safely and passed as argv, not shell text?
- Are compile/run timeouts, output limits, and executable cleanup sufficient?
- Does multi-file run discovery include intended implementation files without pulling unrelated scratch files?
- Are Linux-target and native Windows run semantics clearly separated?
- Are tests covering traversal, duplicate paths, compiler arg parsing, run path discovery, and toolchain extraction enough?

### Audit B: LSP Bridge and Source Navigation

Scope:

- `internal/app/lsp.go`
- `internal/app/source.go`
- `web/src/lspClient.ts`
- Ctrl+click path handling in `web/src/main.ts`

Questions:

- Does the WebSocket implementation handle close, ping, payload limits, and pending requests correctly?
- Can malformed frames or large messages cause resource issues?
- Does clangd process cleanup happen reliably on disconnect?
- Are read-only include files opened and mapped to Monaco URIs safely?
- Are `didOpen`, `didChange`, and `didClose` notifications consistent when tabs/models are opened, closed, or restored?
- Does reconnect behavior avoid noisy retry loops after intentional shutdown?

### Audit C: Frontend State, UX, and Monaco Integration

Scope:

- `web/src/main.ts`
- `web/src/styles.css`
- `web/src/api.ts`
- `web/src/types.ts`

Questions:

- Are file explorer operations, tabs, inline rename, delete, and active file state consistent after refresh?
- Does `localStorage` handle malformed or stale data without breaking the UI?
- Do layout resizing, hidden panes, font zoom, scrollbars, and responsive behavior avoid overlap and stale Monaco layout?
- Are compile/run request IDs handled so stale responses do not overwrite newer UI state?
- Are Monaco models disposed only when appropriate?
- Is CSAPP/raw assembly display readable and stable?

### Audit D: Build, Packaging, Documentation, and Git Hygiene

Scope:

- `scripts/build.ps1`
- `scripts/fetch-llvm.ps1`
- `README.md`
- `docs/architecture.md`
- `.gitignore`
- generated static asset handling

Questions:

- Does the build script produce a reproducible `dist/mini-godbolt.exe`?
- Does the LLVM fetch script verify official download integrity and create the correct embedded zip shape?
- Are release prerequisites documented accurately?
- Does `.gitignore` exclude generated artifacts without hiding important source files?
- Are README and architecture docs aligned with actual endpoints and runtime behavior?

## PM/Subagent Workflow

1. PM performs a local investigation first and updates this file when the pipeline changes.
2. PM launches subagents only after the audit scopes are concrete.
3. Use explorers for read-only audits.
4. Use workers only for bounded edits with explicit file ownership.
5. Do not assign the same write scope to multiple workers.
6. While subagents run, PM continues non-overlapping local work or verification.
7. PM reviews all returned findings before changing code.
8. PM decides which findings are real defects, which are design tradeoffs, and which need user input.
9. PM implements accepted fixes or creates a focused follow-up plan.
10. PM runs verification and reports residual risk.

## Audit Report Format

Each subagent report should use this structure:

```text
Findings
- [severity] file:line or function: concise issue

Evidence
- What code path creates the risk.

Recommended Fix
- Minimal change that addresses the issue.

Verification
- Command or UI workflow that should prove the fix.

Residual Risk
- Anything not covered by the audit.
```

Severity guide:

- Critical: arbitrary file write/read outside allowed roots, arbitrary command execution beyond intended clang invocation, or persistent data loss.
- High: reproducible crash, broken release build, unsafe toolchain extraction, or compile/run behavior that violates the app contract.
- Medium: stale UI state, LSP lifecycle bugs, misleading diagnostics, incomplete cleanup, or missing tests for important behavior.
- Low: polish, documentation drift, minor UX inconsistency, or test coverage gaps without immediate behavioral breakage.
